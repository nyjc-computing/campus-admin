Each service's database migration plan (the revisions a human approves before applying) and ledger history. Apply runs in the service's background; abort takes effect between migrations; rollback undoes one applied revision where the migration declares support. This is the manual production surface — on the development deployment migrations auto-apply at startup, so a healthy section reads everything up to date.

Authority (two-leg model): acting here needs an access-grant row designating you for migrations:read / write / admin on the service (production grants are seeded ahead of a migration window) and the matching scope on your campus token — the services enforce both on every action, so the buttons below are convenience only. The api and audit sections stay blocked until campus.auth surfaces token scopes to services (campus#1183); their caveats are expected, not faults in this view.
